# Gemini Streaming Adapter Findings

This document tracks learned information regarding adapting AG-UI stream message formatting to native Gemini architectures via `@google/genai`. 
**Note:** This is an experimental stage, therefore communication patterns have been minimally reduced to unblock immediate technical progress. Future logic should read and extend these findings!

## Design Decisions

1. **Stripping System & Developer Messages:** 
   Our current `geminiMessageFormat.toApi()` proactively filters out and discards AG-UI `SystemMessage` (`role: "system" | "developer"`) entries! We stripped these out experimentally because the Gemini API restricts conventional dialogue turn roles strictly to `"user"` and `"model"`. It is presumed that the calling context provisions the `BidiGenerateContentSetup.systemInstruction` out-of-band beforehand prior to this conversion matrix mapping history. *Future experimentations should verify if dynamic re-injection is desired over Websockets!*

2. **Native Typings Implementation:**
   The intermediate IO format for Gemini (`GeminiMessage[]`) relies specifically on referencing the `Content` structure directly exported out of the `@google/genai` library ecosystem. This provisions the core interface map indicating explicitly how Gemini expects to consume arrays mapping (`role`, `parts[]`), instead of mimicking external interface signatures.

3. **Function / Tool Response Grouping:**
   Achieving absolute structural correctness is enforced aggressively since this pipeline outputs directly into downstream rendering engines relying heavily on this schema. We replicate the identical `vercel-message-format` protocol: consecutive single instances of `ToolMessage` are aggregated inside a unified `Content` block tagged as `"user"`, compiling an array of respective `functionResponse` fragments into a single interaction turn.

4. **Media Payload Format:**
   AG-MIME structures (`BinaryInputContent`) translate optimally into Gemini by mapping them natively down into `inlineData`. It was explicitly chosen to map straightforward base64 encodings inside `inlineData` because of immediate structural consistency and simplicity rather than risking complex file-uri schema optimizations. Subsequent enhancements will iterate upon handling massive video/audio BLOB optimizations securely.
